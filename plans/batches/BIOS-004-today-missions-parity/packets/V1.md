# Packet V1 — ProgressRing (svg + Reanimated ring, honesty states, reduced-motion)

## Objective

Create the **ProgressRing** viz primitive — the first component in Wave 1 of the BIOS-004 packet decomposition (architecture-plan.md §5, row `1a`). It is a stroke-animated SVG ring (react-native-svg `Circle` + Reanimated `useAnimatedProps` on `strokeDashoffset`, per **ADR-1**) that:

1. Sweeps `0 → progress` on mount (520ms, physical easing) and re-sweeps on later progress changes (250ms) — **unless** the device has reduced-motion enabled, in which case it renders the final static state instantly (canon: "text updates and haptics still occur" but no sweep).
2. Renders one of three **honesty states** (`real` / `low` / `null`) per **ADR-2** — never fabricates a numeric readout when the underlying metric is null.
3. Supports the **numeric-KPI variant** (`centerLabel`, tabular-nums) and the **ambient-frame variant** (`glyph`, e.g. a badge emblem for S42 celebration) per the catalog's two documented `ProgressRing` variants.
4. Is consumed downstream by `GlassStatCard`'s `ring` variant (packet 1c) and directly by the Today/Missions/mission-detail/celebration screen packets (waves 4a–4c) — this packet does **not** wire any of those consumers.

This is the first component to use `react-native-svg` and `react-native-reanimated` together in this codebase (verified live — see §"Verified live facts" below) — it is also the empirical gate for **Risk #1** in architecture-plan.md §7 ("verify `createAnimatedComponent(Circle)` + `useAnimatedProps(strokeDashoffset)` works before fanning out charts").

### Resolved ambiguities (binding for this packet — the contract above leaves these open; do not re-derive differently)

The plan's one-line contract comments (`orange until 100, green at 100`; `null=ghost ring + honest copy via caller`) under-specify exact runtime behavior for a component with no prior art in this codebase. These rules are binding, not suggestions:

1. **Stroke color resolution** (evaluated in this order):
   - `state === 'null'` → no colored arc is drawn at all (see rule 3). `glow` is ignored entirely.
   - `glow === 'cia'` → `BalenciaColors.purple`, regardless of `progress` (purple is reserved for Cia/AI surfaces per ADR-2 — the caller opted into this glow explicitly, so it does not auto-flip to green at 100%).
   - `glow === 'done'` → `BalenciaColors.green`, regardless of `progress` (explicit completed/celebration framing — e.g. the S42 ambient badge-frame usage, which is always inherently "done").
   - `glow === 'you'` (default) → `BalenciaColors.orange` while `progress < 100`, `BalenciaColors.green` once `progress >= 100` — this is the literal "orange until 100, green at 100" behavior and is the only variant that auto-flips.
2. **`state === 'low'`**: render normally (per the color resolution above) but at `opacity: 0.64` on the animated arc — matching this design system's established low-confidence convention (`GlassStatCard`/`KPIRow` "KPI at 64%" pattern, quoted three times in the Design spec section below). Apply the same `0.64` opacity to `centerLabel`'s `Text` if rendered in this state. The track circle is unaffected (stays full-opacity `chartTrack`).
3. **`state === 'null'` (honest-null)**: render the track circle only (`BalenciaColors.chartTrack`, full opacity — its own alpha is already faint enough to read as "ghost"; do not invent an additional ghost-specific opacity value on top of it — the design docs give no such number and precision must not be fabricated, mirroring `motion.ts`'s own documented refusal to invent spring physics the specs don't state). Draw **no** progress arc (equivalent to a 0%-swept arc, or simply omit the animated `Circle` for this state — either is acceptable, the visual result must be identical: track only). **`centerLabel` is not rendered in this state, even if the caller passes a non-null string** — a null-state metric must never surface a number (the honesty invariant, COMPACT-CANON §7: "Never invent a number"); the caller is responsible for placing honest-null copy (e.g. "3 more days") near the ring, not inside it. `glyph` **is** still rendered if provided in the `null` state — a glyph is decorative chrome (e.g. a badge outline), not a fabricated metric value, so it is not honesty-gated.
4. **Mount vs. update animation duration**: `animateOnMount` gates only the *very first* render's `0 → progress` sweep (520ms, `MotionDuration.sweep`). Any subsequent change to the `progress` prop after the component has mounted animates over `MotionDuration.sweepShort` (250ms) — this is the "re-sweep on completion" behavior from spec S14 ("on completion, shorter 250ms re-sweep") and is **not** gated by `animateOnMount` (that prop only concerns the initial mount). Both animations use `MotionEasing.physical`. If `useReducedMotion()` is `true`, or `animateOnMount === false` on first mount, skip straight to the final numeric value with no animation (Reanimated `useSharedValue` set directly, not `withTiming`) — this applies to both the initial mount case and every later update, per ADR-6.
5. **`stroke` is NOT clamped.** Only `progress` carries the contract's `(clamped internally)` annotation — clamp it with `Math.min(100, Math.max(0, progress))` before using it anywhere (geometry, accessibility value, color-flip check). `stroke`'s `// 6..8` comment is usage guidance for callers, not a runtime constraint; do not add clamping logic for it that the contract does not ask for.
6. **`centerLabel` vs. `glyph` priority** (outside the null state, where rule 3 already forces no label): if `centerLabel` is a non-empty string, render it (`Text`, `fontVariant: ['tabular-nums']`, per the contract's "tabular-nums KPI" comment). Else if `glyph` is provided, render it centered in the ring. Else render nothing in the center (bare ring — a valid state, e.g. a purely decorative/dense list-row ring with no room for a label).
7. **Non-interactive by contract.** This contract has no `onPress`/`onLongPress` prop. Do not wrap the ring in `Pressable`/`TouchableOpacity` or add any touch handler — `ProgressRing` is a leaf visual primitive; the 44px interactive-target rule (see preamble quote above) is satisfied by whatever `Pressable` *ancestor* embeds this ring (a `SolidCard` mission row, a `GlassStatCard`) in the screen-composition packets (waves 4a–4c), not by this component itself.
8. **Geometry**: `radius = (size - stroke) / 2`; `circumference = 2 * Math.PI * radius`; SVG `Circle` `strokeDasharray={circumference}`, animated `strokeDashoffset = circumference * (1 - clampedProgress / 100)`, `strokeLinecap="round"`. Start the sweep at 12 o'clock, clockwise (rotate the ring −90°, e.g. wrap the `Svg` in a `View` with `style={{ transform: [{ rotate: '-90deg' }] }}`) — this is the universal ring-progress convention and matches every reference screenshot's visual orientation in `Balencia-New-Screens/build-progress/screenshots/` (12/13/14/42 pinned-mission and hero-ring renders all start top-center).
9. **Reanimated wiring** (lint rule from `_worker-rules.md`, binding): use `useSharedValue` for the animated progress value — **never** read/write a `ref.current` during render. `const AnimatedCircle = Animated.createAnimatedComponent(Circle);` then `useAnimatedProps(() => ({ strokeDashoffset: ... }))` bound to the shared value; drive the shared value with `withTiming(target, { duration, easing: Easing.bezier(...MotionEasing.physical) })` (import `Easing` from `'react-native-reanimated'`, not from `'react-native'` — `motion.ts`'s header comment explains why the bezier tuple is a plain array, not a pre-built `Easing` curve, in that file).
